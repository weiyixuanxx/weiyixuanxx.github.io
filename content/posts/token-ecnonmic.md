在 vibe coding 的时候，我发现很多人对于 token 的消耗完全没有概念。
其实这里面就有之前的我，我刚开始使用 codex 和 claude 这类 AI 编程工具的时候，
花 token 总是大手大脚的，结果一回头发现，几天没到居然一千多块钱就花出去了。。。

生于忧患，死于安乐。我们编程者一定要做到未雨绸缪，以最经济的方式进行 vibe coding , 用最少的 token 干更多的事情。不然最后一看账单，则悔之晚矣。

    （我们所说的内容都是针对按 token 计费的人群，不是按照其他方案使用 AI 的人群）

## 1. prompt 的 token 消耗量

我们先来看看一段 prompt（就是你给大模型的那些话）的 token 消耗量。 prompt 的 token 消耗量取决于其长度。具体来说，**prompt 的 token 消耗量 = 字数 / 4。**

一个显而易见的经验是，**一次不要编写太长的 prompt**。这一点很多人都能够想到，输入 1000 个字符的 token 消耗量大约就是 250 ，输入 10000 个字符的 token 消耗量大约就是 2500。

但是有很多人意识不到自己正在写过长的 prompt 。在 coding 时，他们一旦遇到某些问题，就会经常的大段复制粘贴，结果就是，他们的 prompt 太长了，甚至长到 AI 要把这些 prompt 中很多的一部分转化为文件。这是一个很浪费 token 的做法。

## 2. 文件读取的 token 消耗

接下来的部分就是绝大多数人意识不到的情况。他们可能会怀疑：“明明我的 prompt 写的足够简短，为什么 token 花费还是这么高？”

是的，也许你的 prompt 写的确实够短，但是 AI 可不仅仅只阅读你的 prompt。现在 vibe coding 都采用的是 coding agent，而 agent 是可以进行 function call （调用一些工具来辅助完成任务）的，也就是说，除了读你的 prompt 之外，AI 还往往要读取其他的文件。

而每读一个文件，**整个文件的 token 消耗量也是 token 消耗量 = 文件字符数 / 4。**，也就是说，如果你的 prompt 里面要求 AI 读取一个 100000 个字符的文件，那么这个文件的 token 消耗量就是 25000，这个文件的 token 消耗量甚至比你的 prompt 还要高的多！

所以，我们在写 prompt 的时候，一定要具体。假如代码哪里有问题，就把具体的文件和行号指出来，防止 AI 为了解决你的问题，读取了很多不必要的文件。

有些朋友还有一个坏习惯，就是面对自己从来没有见过的一个项目的时候，总喜欢让 AI 大段大段的去进行相关内容的解释分析，结果就是，AI 为了完成对于项目的理解，往往需要阅读很多很多的内容，这样，它的 token 消耗量就会爆表，有时往往超越 agent 完成 coding 任务的 token 消耗量。

对于这些朋友，我的建议是：下次能自己搞明白就不要问 AI，即使要问 AI，最好也是问诸如 “这个函数的作用是什么？” 而不是 “帮我解释整个文件” 这样的话。

## 3. AI 写文件的 token 消耗

接下来就是写文件了。写文件的 token 消耗量是非常高的，因为**每写一个字符，就是 +1 的 token 消耗量。**

但是，让 AI 来写文件，不就是 coding AI 的核心任务吗？很遗憾，这里有时候就是要消耗浪费 token，躲不过去的，最节省token 的方式，只能是设计出一个最完美的项目。

不过，俗话说的好，“好钢用在刀刃上”，我们写代码的时候，一定要想到 token 的消耗，要精明点。**能改一次，不改十次**，认认真真写 prompt ，把需求都明确下来，让 ai 懂得你想干什么，一次性就能完成任务，而不是反反复复的修改才完成任务。

这里需要 coding 的人从 vibe coder 转变为 spec coder。什么是 spec coder ？就是会写最好的 prompt 的人。 spec coding 是把一个大任务拆解/重构为很多小任务，然后让 ai 完成这些小任务，每一步都可以交付和验证。这样做往往比使用 vibe coding 最后搞出一个屎山要省更多的 token。

## 4. 编写 skill 的 token 消耗

别忘了，skill 也是会消耗 token 的。很多人 vibe coding 会非常依赖于 skill，但是 skill 的本质也是一个读文件，每次读一次 skill 也要消耗大量的 token。

大家在编写 skill 的时候，尽量考虑压缩 skill.md 的字数和调用次数，不要让 skill 浪费了太多 token 。
